TL;DR
--------------------------------------------------------------------------------

  SCAN-FLAG byte in the BSGalaxy::PlayerKnowledge component at db+0x268, slot
  +0x21, keyed by the bare SPECIES formID (FNV-1a over the 4 formID bytes). It is
  a SAVED galaxy component; fresh instances re-derive their key deterministically
  from their base-form (species) formID on reload — no timestamp, no catalog.

  rebuilt empty per load" are CORRECT — but ONLY for the db+0x3d8
  DisposableInstancedFormDB path (ID_52161/ID_52162). That path is the DYNAMIC-id
  branch and is genuinely transient. It is NOT the path that persists green.
* REF-FREE WRITABILITY: the persistent flag is FULLY writable for an ARBITRARY

  db+0x268 lookup. No live instance, no current-planet binding required for the

  ref->planet resolution, which the ref-free path bypasses by supplying planetId.

THE TWO STATE LAYERS AND THEIR THREE COMPONENT DBs (TYPE PROOF)
--------------------------------------------------------------------------------
The knowledge manager (ID_126578() -> +0x8b0 = db) owns three BSComponentDB2
containers. RTTI type descriptors confirmed in the program DB:

  db+0x268  BSGalaxy::PlayerKnowledge          <- PERSISTENT (saved galaxy knowledge)
  db+0x3d8  DisposableInstancedFormDB::DBTraits <- TRANSIENT ("Disposable")

"Disposable" is in the type name. That is the catalog the prior verdict found to

"PlayerKnowledge" is a saved galaxy component; it is the survey knowledge that
persists across save/load. (ID_52204 / ID_52153 / ID_46756 build their writes as
BSComponentDB2 CreateAndDeleteCommand objects targeting these containers; the
PlayerKnowledge container is the one the save serializes.)

Q2 — THE KEY ON RELOAD (how a fresh instance resolves green)
--------------------------------------------------------------------------------
A fresh instance on reload resolves its green WITHOUT any per-instance state:

  * ID_36022(base+0xc8, 0x2a) is a property of the BASE FORM (the species), not
    the instance. Identical for every instance of a species.
  * If bit clear: ID_83007 reads the PlayerKnowledge per-planet flag for the ref's
    planet (resolved from the ref's location) -> the SAVED scan-flag the real scan
    wrote -> GREEN, for any instance, fresh or not.
  * If bit set + static id: ID_52159 reads the SAME saved per-species flag at
    subobj+0x60 slot +0x21, keyed by ID_124901(speciesFormID). Deterministic;
    every instance of that species on that planet resolves to the same slot ->
    GREEN.

ID_137052 (the per-call timestamp minter, canonical-key.txt:1) is reached ONLY
from ID_52161 (the dynamic-id catalog/tree writer), and only when the base form
returns {0,0,0} from vtable[0x15]. The REAL persistent scan path (ID_52158) NEVER
calls ID_137052. So the "different timestamp per instance" problem the prior
verdict identified simply does not arise for the persistent flag. The deterministic
key source is ID_124901(speciesFormID) — the species formID itself.

This is fully consistent with the public gameplay model and the ground truth:
scan N separate instances -> the per-(planet,species) flag saturates to 100% ->
the SAVED flag greens ALL instances of that species on that planet, now and on any
future launch, including brand-new spawns.

Q3 — REF-FREE WRITABILITY FOR A TARGET PLANET
--------------------------------------------------------------------------------
WRITABLE. The persistent green flag is producible ref-free for an arbitrary target
planet. It is NOT location-bound.

Why the prior "on-planet only" claim does not apply to the persistent flag:
  * ID_52188 (planet-resolver.txt / planet-survey-internals.md) resolves a planet
    from a ref's LOCATION (ExtraData 0x81, else position). That binding only
    matters when you drive the scan THROUGH a ref (ID_52157/ID_52160 call ID_52188
    to learn which planet to credit) -> credits the planet you stand on.
  * The persistent writer ID_124898 takes (subobj, speciesFormID, delta). subobj
    is resolved purely from the planetId you put in the db+0x268 key. Supply the
    TARGET planetId and you write the target planet's saved flag directly — no ref,
    no ID_52188, no current-planet binding.

CONCRETE REF-FREE RECIPE (no spawn, no being-on-planet) for one target planet:
  1. manager = ID_126578();  db = *(manager + 0x8b0).
  2. key = ((uint64)ID_938333 << 48) | ((uint64)targetPlanetId << 16).
  3. ID_126806(db + 0x268, out[4], &key) -> resolve per-planet entry. If miss
     (out[3]==0xfe0 && out[2]==0): the planet has no knowledge component yet; you
     must first create it. The engine creates it lazily on first write via the
     CreateAndDeleteCommand path (ID_52204 / ID_124898's "insert if missing" arm).
     ID_124898 itself creates the slot if absent (real-scan-chain.txt:575-615).
     For a never-touched planet, drive one write through the engine's own
     create path or call the same ID_1016657/ID_97851 population the mod already
     uses, then write the flags.
  4. subobj = entry + 0x20.
  5. For each species formID S on the target planet (enumerated from the ESM /
     from the ID_1016657 aggregator buffer):
        ID_124898(subobj, S, 0xFF)        // saturate scan-flag at slot +0x21
        (optionally ID_124899(subobj, S, 100) for the percent byte at +0x20)
  6. Fire ID_97853(ctx) so the completion event/slate transitions (see internals).

This writes the EXACT saved per-(planet,species) flag the real scan writes. On
the next cell load of that planet, every flora/fauna instance whose base form is
that species resolves through ID_83007 (bit clear) or ID_52159 (bit set + static)
to this saved flag and renders GREEN — fresh instances included. That is the
ground-truth behavior, reproduced ref-free.

CAVEAT — the cosmetic dynamic-id tree (ID_52162 path) is NOT writable ref-free and
does NOT need to be. It is the DisposableInstancedFormDB catalog + subobj+0x60
RB-tree, keyed by a per-instance timestamp via ID_137052, rebuilt per load. The
prior verdict is correct that you cannot hand-stamp it for fresh instances. But it
is transient and only affects the CURRENT session's already-spawned dynamic refs;
it is regenerated by the engine on each load FROM the per-species data the renderer
gates on. The persistent green does not depend on it.
