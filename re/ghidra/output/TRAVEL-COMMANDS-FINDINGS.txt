================================================================================
WHY lop / lopb / TakeOffToSpace SILENTLY NO-OP FROM THE CONSOLE
Starfield.exe 1.16.236 (Ghidra project "Starfield", Address Library ID_<n> labels)
================================================================================

ROOT CAUSE (one line)
---------------------
All three console commands are registered with an executeFunction that is a
2-byte stub:  ID_35677 @ 1402b7950  =  "MOV AL,1 ; RET"  (return true, do nothing).
There is NO precondition that fails -- there is simply NO execute-time
implementation. The console run-path calls a function that does nothing and
reports success. (See stub-35677.txt.)

The registrar ID_67259 @ 140c8d550 copies exactly 0x58 bytes per entry into the
runtime BSTArray (singleton getter ID_67262 @ 140c8d880, backing array ID_945979,
reserves 0x613 entries * 0x58). Stride 0x58 verified. (See cmd-registrar.txt.)

THE STUB IS A SHARED PLACEHOLDER (not unique to travel)
-------------------------------------------------------
ID_35677 is referenced as DATA (stored as a function pointer into command structs)
from MANY console-command registrars: ID_7980, ID_7982, ID_2763/2764/2765,
ID_21654, ID_71807, ... (stub-xrefs.txt). It is the engine's default
"do-nothing execute" used by every console command whose behaviour is implemented
through another subsystem rather than the SCRIPT_FUNCTION execute path.

WHY THE COMMAND APPEARS TO "PARSE BUT DO NOTHING"
------------------------------------------------
- compileFunction = ID_65846 (StandardCompile) DOES run and validates the args.
  -> malformed args ("lop" with a bad form / wrong type) would print an error.
  -> well-formed args ("lop Kreet 0 0 deg") compile fine, then execute = no-op.
  That is exactly the user's symptom: typed correctly, zero feedback, nothing happens.

WHERE THE REAL LANDING/TAKEOFF LOGIC LIVES (UI / menu / event path, NOT console)
-------------------------------------------------------------------------------
The actual flows run through the Star Map / ship menu + movement-message system,
entirely separate from the console command table. Evidence (landing-impl-xrefs.txt):
  - "TakeoffMenu", "TakeoffMenu_Launch", "TakeoffMenu_ExitShip" (UI menu events)
  - "FlightTakeOffHandler", "SpaceshipTakeOffFinishedHandler",
    "TakeOffInitiateCompleteHandler"  (handler ID_103932 @ 141ae2910)
  - "SpaceshipTakeoffMode" global (refs in ID_162/164/171/175/119788)
  - PathingRequestFlyTakeOff / MovementMessageTakeOff factory machinery
  - "PreventPlayerLandingAtMarker_DO", landing-marker plumbing
None of these are reachable by invoking the stubbed console executeFunction.

VERDICT: CAN THESE BE DRIVEN PROGRAMMATICALLY FROM AN SFSE PLUGIN?
-----------------------------------------------------------------
Calling the console command (or its executeFunction at +0x30) from a plugin is
POINTLESS -- it is MOV AL,1; RET. There is no global to set and no precondition to
satisfy that would "unlock" it, because there is no command body at all.

To actually land/take off from a plugin you must drive the SAME path the Star Map
uses, NOT the console command:
  * Preferred / robust: trigger it from Papyrus, where real functions exist
    (e.g. Actor/Spaceship/Planet land/takeoff and FastTravel script functions and
    the Takeoff menu events). An SFSE plugin can call into Papyrus or post the
    same UI/menu events (TakeoffMenu_Launch, etc.).
  * Native: replicate handler ID_103932 @ 141ae2910 (Flight/Takeoff handlers) and
    the SpaceshipTakeoffMode / PathingRequestFlyTakeOff machinery, or call the
    same native landing entry the Star Map "Land here" button calls. This is
    feasible from CommonLibSF but requires RE of those handlers + the player/ship
    state they expect (player piloting, ship space-borne, valid target body in the
    current system) -- those checks live in the UI/handler path, not in any console
    precondition you can pre-set.

Bottom line: the bare console invocation fails because the command is an
intentional no-op stub, not because of an unmet precondition. A plugin cannot
"fix" the console command; it must invoke the Star-Map/menu landing path
(easiest via Papyrus functions / Takeoff menu events) instead.
