THE TWO RECORDS, AND WHY ONE IS GREEN AND THE OTHER IS DATA
================================================================================
Everything hinges on bit 0x2a of the species BASE form, read by ID_36022(base+0xc8,
0x2a) at the TOP of BOTH the reader ID_83007 (scanned-state.txt:26) and the writer
ID_83008 (scanned-state.txt:132). This bit selects which record represents "scanned"
for that species:

  bit 0x2a CLEAR  -> the ScannableComponent path (type ID_939118), keyed by REF id.
  bit 0x2a SET    -> the +0x21 per-(planet,species) survey hashmap (type ID_938333),
                     keyed by species id (static) or the transient db+0x3d8 tree
                     (dynamic id).

Biome flora/fauna take the CLEAR branch (F1+F2 jointly force this: writing the +0x21
hashmap, which is the SET branch's record, yields data-complete-but-blue; the green
the real scan produces must therefore be the CLEAR-branch record).

RECORD A — ScannableComponent (type ID_939118) = THE PERSISTENT GREEN
  * Container: db+0x268 (the SAME saved container as the survey hashmap; ID_52204,
    spoof-investigation.txt:333, builds CreateAndDeleteCommand<...PlayerKnowledge>
    into +0x268 -> this container is the SAVED galaxy knowledge).
  * Key: (ID_939118 << 48) | (refFormID << 16). The key's middle 32 bits are the
    SCANNED REF's OWN formID — *(param_1 + 0x28) — NOT the planet, NOT the species.
    (scanned-state.txt:41 reader; 134/139 writer via ID_83038.)
  * Created by ID_83004 (scan-component-lifecycle.txt:1) and ID_83005
    (spoof-globals.txt:26): both stamp a StoredComponent<1, ScannableComponent>
    (RTTI string in the decompile) into db+0x268. ID_83005 writes:
       +0x18/+0x1c  the ref formID and a SECOND id uVar9 = *(param_2 + 0x28)
                    (a related/owner ref), and crucially
       enum ScannableUtils::InitialScanStatus  (the +0x14 byte param_3).
    ID_83004 sets puVar5[4] = CONCAT44(canonicalId, refId): the component stores
    BOTH the raw ref id (+0x20) and a CANONICAL/known species id (+0x24).
  * Scanned flag: ID_83038 (real-scan-chain.txt:477) writes *(entry + 0x28) =
    *param_2 (the scanned byte) and, when set, copies the canonical id from +0x24
    into *param_2[1] (the out-param ID_83008 then feeds to ID_52157). So +0x28 of
    the ScannableComponent = the boolean "this thing is scanned" the renderer reads.
  * Render reader: ID_83007 bit-CLEAR branch (scanned-state.txt:43-50):
       resolve db+0x268 by (939118, refId); return 1 + (entry+0x28 byte != 0).
    Return 2 = scanned/green, 1 = known-but-unscanned/blue, 0 = not a biome ref.
    This is the value the outline renderer keys green on.

RECORD B — survey hashmap slot (type ID_938333) = THE DATA / SURVEY %
  * Container: db+0x268, key (ID_938333 << 48) | (planetId << 16) (per-planet entry).
  * subobj = entry + 0x20; species hashmap @ subobj+0x18, slots @ subobj+0x40,
    PERCENT byte +0x20, SCAN-FLAG byte +0x21, keyed by SPECIES id (FNV-1a, ID_124901).
  * Written by ID_124898/ID_124899 (what the mod's MarkSpeciesScannedForPlanet does).
  * Read by GetSurveyPercent / ID_97851 (spoof-investigation.txt:383): ID_97851 walks
    the planet's flora/trait/resource id arrays and counts species whose +0x21 byte
    >= threshold -> the "X% surveyed / BIOME COMPLETE" number. NOTHING in ID_97851
    reads or sets the ScannableComponent +0x28. This is why F2's +0x21 write makes the
    planet read complete but renders nothing green and re-scanning still awards XP:
    the XP/green gate is Record A, untouched.

NET: Record A (per-ref ScannableComponent, +0x28) = the GREEN. Record B (per-planet
species hashmap, +0x21) = the survey DATA. They are different records, different keys,
different readers. The superseded verdict conflated them.

Q1 — HOW A FRESH INSTANCE (NEW formID) RESOLVES TO GREEN AFTER RESTART (F1)
================================================================================
This is the subtle part and it is the reason the spoof fails. Record A is keyed by
the SCANNED ref's formID, but a freshly-spawned instance on reload has a DIFFERENT
formID, so a naive per-ref lookup would miss. It does not miss, because the resolve
is SPECIES-mediated, in two layers:

  1. The ScannableComponent stores at +0x24 the CANONICAL/known species id (ID_83004
     puVar5[4]=CONCAT44(canonicalId,refId); ID_83009 spoof-globals.txt:171 returns
     entry+0x24 as the "scanned species id" for a ref). On a fresh instance, the
     engine re-derives the ref->species and looks up the saved ScannableComponent for
     instances of that species.
  2. ID_83011 / ID_83013 (scan-component-lifecycle.txt:139/206) iterate a planet's
     live refs, map each via ID_47401(refId)->base, take the ScannableComponent's
     +0x24 canonical id, then look up the species in the +0x38/+0x60 hashmap reading
     the +0x20 byte. This is the per-species "have I scanned ANY instance of this
     species" rollup that lets a fresh instance render from prior scans.

The decisive property: the persistent green is, functionally, PER-SPECIES (galaxy-
wide), not per-(planet,species). A scanned species greens its instances wherever they
appear, because the gate is "is this species' ScannableComponent present+flagged",
re-derived from the base form on reload. That matches F1 (fresh instances green) and
explains the "green PERSISTS per-TYPE" memory note. It also means the planet the ref
was physically on, at scan time, does NOT key the green — it only keys the Record B
survey DATA via ID_52188.

Q3 — THE SPOOF: VERDICT = NOT VIABLE FOR PERSISTENT GREEN (decompiled blocker)
================================================================================
Question restated: temporarily set the current-planet global to TARGET, run the
genuine real scan on a sample instance spawned at the player on the CURRENT planet,
restore the global — does the real scan write PERSISTENT green for the TARGET planet?

ANSWER: No — not in the sense intended ("green that target planet specifically").
The blocker is structural, not a missing-biome problem:

1. The real scan's PERSISTENT-green write (ID_83038 -> ScannableComponent +0x28,
   scanned-state.txt:139) does NOT consult ID_52188 and does NOT consult
   ID_937609+0x80 AT ALL. It is keyed purely by (939118, refId) and rolls up to the
   SPECIES. Spoofing the current-planet global changes NOTHING about that write —
   the green it produces is the species' galaxy-wide green, identical whether the
   global is spoofed or not.
   => Overwriting ID_937609+0x80 cannot REDIRECT the green to a target planet,
      because the green was never bound to a planet to begin with. (Confirmed:
      ID_83008 cVar==0 branch, scanned-state.txt:133-142 — the ID_83038 call takes
      no planet; only the SUBSEQUENT ID_52157 (Record B/data) takes a planet, and
      that planet comes from ID_52188 on the ref, which the spoof would move.)

2. What the spoof DOES move is ID_52157/ID_52158 -> Record B (the +0x21 survey DATA).
   But F2 already proved Record B is greenless. So the spoof buys exactly the
   data-complete-but-blue state the mod can already write ref-free with
   ID_124898/ID_124899 — no spawn, no spoof needed.

3. The "does it need the biome materialized?" sub-question: ID_52158's biome half
   (real-scan-chain.txt:251-308) reads ID_937609+0x160, which is empty for an
   un-landed target, so that half no-ops — but that half is in-session propagation,
   not persistence, so it is moot for green either way.

CONCLUSION ON VIABILITY: The current-planet global (ID_937609+0x80) is real, found,
and writable, and spoofing it WILL redirect the per-planet survey DATA credit. It
will NOT redirect the persistent green, because the persistent green (the ID_939118
ScannableComponent) is per-SPECIES, ref-keyed, and planet-agnostic — there is no
planet field on it to redirect. The decompiled blocker is: ID_83038 (the green
writer) takes no planet input and is not downstream of ID_52188/ID_937609+0x80.

WHAT ACTUALLY REPRODUCES F1 GALAXY-WIDE (the correct lever)
================================================================================
Because the persistent green is per-SPECIES (Record A, ScannableComponent +0x28,
keyed by ref id, rolled up by the +0x24 canonical species id), the genuine,
F1-faithful way to green a species EVERYWHERE is to make its ScannableComponent
present+flagged ONCE — which the real SetScanned on ONE live instance already does,
and which then greens that species on every planet that hosts it on reload (per-TYPE
persistence, per the memory note). You do NOT need to be on, or spoof, each target
planet for the GREEN; you need it once per SPECIES.

Concretely, to fully complete a planet the mod must write BOTH layers:
  * Record B (DATA / survey %): ref-free, per planet — ID_124898/ID_124899 +
    attribute bits (already done by MarkSpeciesScannedForPlanet / WritePlanetSurveyState).
  * Record A (GREEN): per SPECIES — produce the ScannableComponent for each species.
    The only engine entry that writes Record A is the real SetScanned/ID_83008
    cVar==0 path (-> ID_83038 -> ID_83005's CreateAndDeleteCommand<...ScannableComponent>),
    which requires a LIVE instance of the species (PlaceAtMe). One live instance per
    UNIQUE species, scanned once, greens that species galaxy-wide. This is precisely
    the EnumerateAllSpecies -> spawn-one -> GreenSpeciesEverywhere shape already in
    src/Main.cpp, EXCEPT the green must come from the genuine ID_83008 ScannableComponent
    write (Record A), NOT from ID_52161 (transient tree, F3) and NOT from ID_124898
    (+0x21 data, F2). The current GreenTypeForPlanet/CompleteTypeForPlanet drive the
    F2/F3 records and therefore green only transiently — consistent with F3.
