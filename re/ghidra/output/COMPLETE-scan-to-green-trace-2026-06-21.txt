PART IV — PROOF biome flora/fauna use Record B (+0x21), reconciling A, B, AND F2
================================================================================
Q: Does the RENDER decider read Record A (per-ref, planet-free) or Record B
   (per-planet +0x21) for biome flora/fauna?
A: Record B. Proof chain:

(i) The persistence + fresh-instance fact (A) RULES OUT Record A as the green source.
    Record A is keyed by the SCANNED ref's formID. A fresh instance on reload has a
    DIFFERENT formID -> Record A lookup misses -> would be BLUE. Yet A says fresh
    instances are GREEN. Therefore the green a fresh instance reads CANNOT be Record A.
    (This is the hole the four prior verdicts never closed; they asserted Record A is
    the green and then could not explain fresh-instance green except by hand-waving a
    "rollup".)

(ii) The render deciders ID_90491 / ID_90548 read Record B, keyed by (player's
     planet, species). ID_90491 does not even consult bit 0x2a or ID_83007 for the
     color — it calls ID_52159(player, species) directly. ID_52159 returns the +0x21
     byte for (player-planet, species). A fresh instance of a scanned species, on the
     planet where it was scanned, re-derives the SAME (planet, species) key and reads
     the SAME saved +0x21 -> GREEN. Deterministic, no per-instance state. This is
     EXACTLY fact A, and it is per-(planet,species) = EXACTLY fact B.

(iii) SAVE FACT B is the +0x21 reader keying on the PLAYER's planet. On planet B,
     ID_52159(player=onB, speciesX) keys (938333|planetB). Species X's +0x21 was
     written only under (938333|planetA). Planet B's entry has no X slot (or 0) ->
     ID_52159 returns 0 -> ID_52180(planetB) membership likely also excludes X (X is
     not authored on B) -> BLUE. PRECISELY fact B. The planet binding is the
     ID_52188(player) call inside ID_52159.

(iv) RECONCILING F2 ("writing +0x21 directly = data complete but BLUE").
     This is the subtle part and it does NOT contradict (i)-(iii). Three independent
     mechanisms can each produce F2 while the model above is correct; the live retest
     must disambiguate, but the static evidence points hard at mechanism (a):

     (a) WRONG SPECIES KEY DOMAIN. ID_52158 (the real scan) writes +0x21 keyed by
         param_1[1] = a species id that the engine RESOLVED canonically (via the
         scanned ref's base form / ScannableComponent +0x24 canonical id, ID_83006/
         ID_83009). ID_52159 at render reads keyed by *(int*)(renderedForm + 0x28) =
         the rendered FORM's formID. For green to light, the formID the RENDER hashes
         must equal the formID the WRITE hashed. If the mod wrote +0x21 keyed by the
         ESM "species form" id (the PNDT/PPBD authored id) but the renderer hashes the
         actually-spawned base-object formID (a different FLOR/NPC_ base form the biome
         materializes), the keys differ and +0x21 is set under the wrong slot ->
         renderer reads 0 -> BLUE, even though GetSurveyPercent (ID_97851), which walks
         the planet's OWN authored id arrays, counts it as complete. THIS EXACTLY
         matches F2's signature "complete data + blue + re-scan still awards XP."
         The real scan does not have this problem because it hashes the SAME canonical
         id on both write and read. => The fix is to write +0x21 under the canonical
         spawned-base-form id, i.e. the id ID_52159 will hash at render time, not the
         ESM authored id (unless they coincide).

     (b) THE +0x20 vs +0x21 / threshold confusion is NOT the cause: ID_52159 reads
         +0x21 RAW (no ID_69506/69507 threshold). ID_97851 (survey %) is the one that
         threshold-compares (ID_69506/69507). So a +0x21 of 100 IS "non-zero" for
         ID_52159. (Ruled out as the F2 cause, but documents that +0x21 must be the
         byte set, which the mod does.)

     (c) ID_52159 first-pass ENTRY-MISSING: if the target planet has no db+0x268 entry
         yet (never visited, never had its PlayerKnowledge component created), ID_52158/
         ID_124898 CREATE the slot on write, but if the mod's write resolved a
         DIFFERENT entry (e.g. created under a stale/zero planetId, or the entry the
         renderer looks up is a freshly-created empty one because the planet's
         component was (re)materialized on landing AFTER the mod's pre-write), the
         render lookup can read the fresh empty entry. Less likely than (a) but worth
         excluding by writing AFTER the planet's knowledge component exists.

Q3 — THE SPOOF / WRITE RECIPE (persistent green for a target planet, ref-free)
================================================================================
The persistent green for a TARGET planet IS writable ref-free, because it is the
+0x21 byte in db+0x268 keyed purely by (planetId, speciesId). You do NOT need to be
on the planet and you do NOT need a live ref for the WRITE. Recipe:

  1. manager = ID_126578() ; db = *(manager + 0x8B0).
  2. For the TARGET planetId:
        key = (ID_938333 << 48) | (targetPlanetId << 16)
        out[4]; entry = ID_126806(db+0x268, out, &key)
        if MISS (out[3]==0xfe0 && out[2]==0): the planet has no PlayerKnowledge entry
            yet. Create it first by driving the engine's own create path once
            (the mod's CompleteAllPlanetsSurveyData / ID_102650 path, or any
            ID_124898 write which inserts the slot — ID_124898 creates if absent,
            real-scan-chain.txt:575). Re-resolve entry.
        subobj = entry + 0x20.
  3. For EACH species S that the RENDERER will hash for that planet:
        ID_124898(subobj, S, 0xFF)      // saturate the +0x21 SCAN-FLAG
        ID_124899(subobj, S, 100)       // +0x20 percent (for the survey-% readers)
     *** CRITICAL (this is the F2 fix) ***: S must be the SAME id ID_52159 hashes at
     render time = the formID at (renderedForm + 0x28) for the species the biome
     actually spawns. That is the canonical base-form / ScannableComponent +0x24
     species id, NOT necessarily the ESM PNDT/PPBD authored "species form" id. If the
     mod currently writes the ESM id and they differ, the data completes (ID_97851
     walks the authored arrays) but the green stays blue (F2). To get green:
        - Resolve the canonical id the renderer uses. Two reliable sources:
          (a) On the planet, spawn one instance, read its ScannableComponent +0x24 via
              ID_83009(ref) — that is the id ID_52159 will hash. Use that id for the
              +0x21 write. (Couples the write to a one-time on-planet probe per species.)
          (b) Off-planet, replicate the engine's ref->canonical mapping: for the
              spawned base form, the canonical id == the value ID_83006/ID_83004 stamp
              into +0x24 (from base-form vtable +0x228 -> ID_83006 -> +0x428). If the
              ESM authored id already equals this (often true for FLOR where the
              authored form IS the spawned base), no remap is needed and the existing
              +0x21 write should green — in which case F2 was mechanism (c) (entry not
              yet created / written under wrong planet), not (a).
  4. (Optional) fire ID_97853(ctx) so the completion event/slate transitions.

What does NOT help and why:
  * Overwriting ID_937609+0x80 (current-planet global) around a real scan: it only
    feeds ID_52188 as the LAST fallback, and at RENDER time ID_52188 is called on the
    PLAYER whose parentCell wins before the global. It also cannot redirect the write
    if the scanned ref's parentCell resolves first. (Matches F3.)
  * ExtraLocation 0x81 on the scanned ref: redirects the WRITE planet (ID_52157 ->
    ID_52188(scannedRef)) to the target, so you can write the target's +0x21 from
    afar — but that is identical in effect to calling ID_124898 directly for the
    target planet. It does nothing at RENDER time (the renderer reads the PLAYER's
    0x81/cell, not the flora ref's). So 0x81 is a write-redirect convenience, not a
    render lever. (Matches the extradata-0x81 verdict's "data yes, but redundant"
    finding — corrected here: it's redundant because the +0x21 write IS the green,
    not because +0x21 isn't the green.)

================================================================================
Q4 — DOES THE GREEN HAVE NO PLANET INPUT? (the reconciliation the task demands)
================================================================================
It HAS a planet input. The green is bound to a planet at BOTH ends:
  * WRITE: the scanned ref's planet (ID_52188(scannedRef)) selects the db+0x268
    entry that gets the +0x21 byte.
  * READ (render): the PLAYER's planet (ID_52188(player) inside ID_52159, invoked by
    ID_90491/ID_90548) selects the db+0x268 entry whose +0x21 byte is read.
The binding is NOT "render-time via the rendered instance's own parent cell" — it is
"render-time via the PLAYER's parent cell/planet" matched against "write-time via the
scanned ref's planet." For ordinary play these coincide (scan where you stand), giving
fact A; on any other planet they diverge, giving fact B. There is therefore NO
contradiction with A or B once the correct reader (ID_52159 via the player) is traced.

The four prior verdicts' "planet-agnostic" conclusion came from tracing ONLY ID_83007
(Record A, per-ref ScannableComponent) and never following the outline deciders
ID_90491/ID_90548 to ID_52159 -> ID_52188(player). Record A genuinely is planet-free,
but Record A is the intra-session per-instance flag, not the persistent green. The
persistent, per-(planet,species), fresh-instance-greening record is Record B (+0x21),
read at render time keyed by the PLAYER's planet. That is the precise planet-binding
point the prior passes missed.
