TL;DR  ——  VERDICT: NO (for the persistent green). PARTIAL YES (for survey DATA).
================================================================================
ExtraData type 0x81 IS honored, and it IS checked FIRST (before ID_56990 and
before the ID_937609+0x80 global). That part of the prior RE is CONFIRMED. So
attaching a 0x81 to the ref DOES let you aim ID_52188 at a target planet without

BUT ID_52188 only feeds the SURVEY-DATA / per-(planet,species) path
(ID_52157 -> ID_52158 -> ID_124898/124899, the +0x21 scan-flag / +0x20 percent).
That path is the SAME greenless "biome complete" DATA the mod already writes
ref-free with MarkSpeciesScannedForPlanet (this is exactly F2/F3's data-vs-green
split). Spoofing 0x81 buys you nothing the ref-free DATA writer doesn't already.

The PERSISTENT GREEN for biome flora/fauna is written by ID_83008's bit-0x2a-CLEAR
branch, which calls ID_83038 ONLY. ID_83038 NEVER calls ID_52188, NEVER reads the
ref's ExtraData 0x81, and takes NO planet input — it is keyed purely by
(ID_939118 << 48 | refFormID << 16) into db+0x268. Therefore NO planet field —
neither the global ID_937609+0x80 NOR the per-ref ExtraData 0x81 — is on the green
write path at all. There is nothing to redirect. This closes the per-ref spoof for
the persistent green, with the same decompiled proof that closed the global spoof.

Q2 — STRUCTURE OF THE TYPE-0x81 EXTRADATA (ExtraLocation), AS READ BY ID_52188
================================================================================
Type 0x81 == RE::ExtraDataType::kLocation == "ExtraLocation"
  (CONFIRMED: ExtraDataTypes.h line 136: kLocation, // 0x81 - ExtraLocation).

ExtraLocation derives BSExtraData, so the first 0x18 bytes are the base
(vtable@0x00, next@0x08, flags@0x10, type byte@0x12). The resolver reads, relative
to the ExtraData node base (lVar2):

  node + 0x18  (u64)  -> forwarded as local_38  (coordinate/aux pair, lo 8 bytes)
  node + 0x20  (u64)  -> forwarded as uStack_30 (coordinate/aux pair, hi 8 bytes)
  node + 0x28  (u32)  -> *param_2  THE PRIMARY PLANET/LOCATION ID  <<< THE LEVER
  node + 0x30  (ptr)  -> if non-null, *(int*)(ptr + 0x28) -> *param_3 (secondary id)

So the value that becomes "the planet" is a UINT32 at node+0x28. ID_56990's 0x81
branch reads the IDENTICAL layout (node+0x28 -> *param_1, node+0x18/0x20 ->
*param_2[0/1]), so the two resolvers agree on the structure.

INTERPRETATION OF +0x28: it is consumed everywhere downstream EXACTLY as the global
ID_937609+0x80 is — as a planetId/NumericID (lower-32 of a BSResource::ID), fed
straight into the db+0x268 key (disc<<48 | planetId<<16). It is NOT a TESForm*,
NOT a BGSLocation* (those are 8-byte pointers; this is a 4-byte id read with
*(int*)), NOT raw coordinates (coords ride in +0x18/+0x20 and are only used by the
geometry fixups). +0x30 is an optional pointer to a related record whose +0x28
yields a secondary id (the "system"/parent component); not required to set the
planet — leaving it 0 makes *param_3 = 0, which the callers tolerate.

NET for a spoof: an ExtraLocation whose +0x28 == targetPlanetId is sufficient to
make ID_52188 return targetPlanetId as the ref's planet, with +0x18/+0x20/+0x30
zeroable (the precise-coords path is only entered when the planet == the one you're
standing on, which a spoofed target is not).

Q3 — CONSTRUCT + ATTACH A TYPE-0x81 EXTRADATA FROM A CommonLibSF PLUGIN
================================================================================
Types available in CommonLibSF:

                               inserter (sets the presence bit + appends to chain).
  RE::TESObjectREFR::extraDataList  BSTSmartPointer<ExtraDataList> @ +0xC8 (==+200),
                               i.e. EXACTLY the pointer ID_52188 dereferences.

CommonLibSF does NOT ship an ExtraLocation class or a constructor for it. There are
two ways to get a node the engine will read as type 0x81:

OPTION A — hand-rolled minimal node (simplest, sufficient for the resolver):
  The resolver only needs: a heap BSExtraData-shaped block with type byte 0x81 at
  +0x12 and a uint32 targetPlanetId at +0x28, linked into the ref's ExtraDataList
  via BaseExtraList::AddExtra (which also flips the presence bit ID_37878 checks).
  Layout to allocate (>= 0x38 bytes, zeroed):
      +0x00 vtable   (can be left 0 for the resolver; see CAVEAT)
      +0x08 next     (AddExtra overwrites)
      +0x10 flags    (0)
      +0x12 type     = 0x81
      +0x18 u64      = 0   (coords aux lo — unused for a non-current target)
      +0x20 u64      = 0   (coords aux hi)
      +0x28 u32      = targetPlanetId          <<< the only load-bearing field
      +0x30 ptr      = 0   (no secondary record)
  Then: ref->extraDataList->AddExtra(reinterpret_cast<RE::BSExtraData*>(node));
  (If extraDataList is null, the engine factory must create it first; flora refs
  PlaceAtMe'd usually have one. AddExtra at ID 44736 operates on BaseExtraList, so
  call ref->extraDataList->AddExtra(...) which wraps it under the RW lock.)
  CAVEAT: a null/garbage vtable is safe ONLY while the node is merely *read* by
  ID_37878/ID_52188 (they never call its virtuals). It becomes UNSAFE if anything
  ever destroys/serializes the ExtraDataList (save, cell unload) — the dtor virtual
  fires. For a transient "attach -> scan -> detach-before-anything-else" window this
  is acceptable; for anything persisted it will crash. Given the verdict below this
  option is moot anyway.

OPTION B — engine-created ExtraLocation (correct, but no CommonLibSF helper):
  Find the engine ctor/factory for ExtraLocation (BSExtraData subclass with type
  0x81) by its vtable in IDs_VTABLE.h / RTTI, allocate via the engine and set its
  location/planet field, then AddExtra. Not needed for this investigation because
  the verdict is NO regardless of how cleanly the node is built.

Q4 — VERDICT: DOES A TYPE-0x81 ON THE REF REDIRECT THE PERSISTENT GREEN?
================================================================================
NO. Decompiled proof, in three load-bearing facts:

(1) THE GREEN WRITE DOES NOT GO THROUGH ID_52188 AT ALL.
    The real scan is ID_83008 (scanned-state.txt:118). For biome flora/fauna the
    species base form has map-marker bit 0x2a CLEAR, so ID_83008 takes the
    cVar==0 branch (line 133):
        ID_83038(playerKnowledge, &scannedByte, &refFormId);   // line 139
        if (scannedByteOut != 0) ID_52157(ref, scannedByteOut, cat); // line 141
    ID_83038 (real-scan-chain.txt:477) is THE persistent-green writer. It builds the
    key  (ID_939118 << 48) | (refFormID << 16)  [line 508], resolves db+0x268, and
    writes the ScannableComponent's +0x28 "scanned" byte [line 515-516]. It takes
    NO planet, never calls ID_52188, never touches the ref's ExtraData. The GREEN
    is keyed by the REF FORMID and rolls up to the species (ID_83009, +0x24 canonical
    id, spoof-globals.txt:171) — it is PLANET-AGNOSTIC. (This is the Record A model
    in green-spoof-verdict-2026-06-21.txt, and it is consistent with F1's "fresh
    instances green per-TYPE on reload".)
    => There is NO planet input on the green write to redirect. A 0x81 on the ref
       changes the green write by exactly nothing.

(2) ID_52188 IS REACHED ONLY ON THE DATA/SURVEY PATH — WHICH F2 PROVED IS GREENLESS.
    The ONLY consumer of ID_52188 in the scan is ID_52157 (real-scan-chain.txt:1,
    called at ID_83008 line 141 AFTER the green write):
        cVar4 = ID_52188(ref, &planetId, &secondary);   // line 43
        ... ID_52158(...)                                 // line 75
    ID_52158 (real-scan-chain.txt:108) resolves the per-(planet,species) survey
    subobj from db+0x268 keyed by THAT planetId and writes ID_124898 (+0x21 scan
    flag) / ID_124899 (+0x20 percent). That is Record B — the survey % / "biome
    complete" DATA. F2 already established writing +0x21/+0x20 yields data-complete-
    but-BLUE. So redirecting ID_52188 via 0x81 redirects only the greenless DATA.
    The READER side confirms the split: ID_83007 (scanned-state.txt:1), the outline
    green decider, on the SAME bit-0x2a-CLEAR branch reads the ScannableComponent
    +0x28 (line 41-50) WITHOUT calling ID_52188; it only calls ID_52188 on the
    bit-0x2a-SET branch (line 74, map-marker species), which biome flora/fauna are
    not.

(3) THE 0x81 LEVER IS REAL BUT POINTS AT THE WRONG RECORD.
    0x81 genuinely beats both the physical cell and the global (Q1), so it WOULD let
    the mod credit a target planet's survey DATA from an unloaded planet without the
    ID_937609+0x80 global trick. But that capability is identical in effect to the
    already-shipped ref-free MarkSpeciesScannedForPlanet (which writes the same
    +0x21/+0x20 directly). It does not, and cannot, move the green, because the
    green write (ID_83038) is upstream of and parallel to ID_52188, not downstream.

CONCLUSION: Attaching ExtraData 0x81 (ExtraLocation, +0x28 = targetPlanetId) to a
spawned ref BEFORE SetScanned does NOT make the real scan write the target planet's
persistent green. It only re-aims the per-(planet,species) survey DATA, which is the
greenless layer the mod can already write ref-free. The persistent green for biome
flora/fauna is ref-keyed (refFormID -> ScannableComponent +0x28) and PLANET-FREE;
there is no planet field on that record for any spoof (global OR per-ref) to
redirect. This is the decompiled blocker, and it does not contradict F1/F2/F3.

  => Per-ref ExtraData spoof for the GREEN: CLOSED (same root cause as the global).
  => Per-ref ExtraData spoof for the DATA: works, but redundant with the existing
     ref-free DATA writer; no spawn/scan needed.
